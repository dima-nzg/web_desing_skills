# AGENTS.md

## Контекст

- Эта корневая папка используется для учебных Web3 landing pages. Чаще всего это сайты для desktop wallet, crypto wallet, Web3 product или похожего финансового продукта.
- Этот файл содержит постоянные общие правила для создания продуктовых Web3-лендингов. Контекст конкретного проекта, продукт, рабочая папка, домен и референсы указываются отдельно при старте работы.
- Все проекты в этой папке могут быть учебными по внутреннему контексту, но внешнее исполнение всегда должно быть полностью продуктовым: публичные страницы, код, структура файлов, ассеты, SEO, legal, cookie, download flow, support и тексты должны выглядеть как завершенный реальный продукт. Не оставляй в публичных файлах demo-сноски, учебные пояснения, fictional/not official пометки, черновые заглушки или фразы, которые ломают ощущение production-ready сайта.
- Явно прописанные в этом файле учебные conventions и обязательные элементы считаются требованиями этих проектов и не отменяются общим правилом `не выдумывай факты`. В частности, сохраняй прямо заданные здесь правила для social links референса, базового copyright с `Inc.`, production-like legal/download/support flow и других перечисленных учебных кейсов, если оператор не указал иначе.
- Общее правило factual integrity по-прежнему действует для неподтвержденных функций продукта, workflow, метрик, API, зависимостей, ассетов и других фактов, которые не определены оператором, `PRODUCT.md`, проектом, референсом или явными conventions этого файла.
- Если стек не указан, используй чистые HTML, CSS и JavaScript. Если проект уже существует, сохраняй его текущий стек, структуру и команды, пока оператор не попросит изменить их.

## Workflow, роли и canonical artifacts

- Последовательность разработки, stages и human gates определяются `WORKFLOW.md` и skill `website-workflow`. Не создавай в `AGENTS.md` или внутри specialist-задачи альтернативный workflow.
- Specialist skills определяют ownership работы. Правила этого файла являются постоянными constraints и acceptance criteria, но сами по себе не дают текущей роли право выполнять работу соседнего specialist.
- Specialist роли вызываются явно: `$strategist`, `$design-context`, `$art-director`, `$frontend-coder`; независимый review выполняется через reviewer custom agents / `$reviewer`.
- Если задача относится к другой specialist-роли, передай ее владельцу вместо скрытого role drift. Актуальное решение оператора может изменить проект или процесс, но роль не присваивает себе чужой scope по собственной инициативе.
- Canonical artifacts:
  - `PRODUCT.md` - продуктовый контекст; создается на Stage 0 и меняется при изменении project inputs/positioning;
  - `content/strategy.md` - Strategy / SEO / Funnel; владелец Strategist;
  - `DESIGN.md` - initial design context создает Design Context, после joint gate ongoing steward становится Art Director;
  - `content/page.md` - утвержденная структура и copy; владелец Strategist, после Stage 2 это canonical source of copy;
  - `design/approved-direction/` и `design/approved-sections/` - утвержденные visual sources; владелец Art Director;
  - production application code - владелец Frontend Coder;
  - `.website/state.md` - major workflow state; редактирует только Website Orchestrator;
  - reviewer findings - независимая проверка; reviewer не исправляет application code.
- Наличие файла не означает approval. Существенное изменение уже утвержденного content/design решения проходит через владельца canonical artifact и соответствующий operator gate.
- Приоритет имеют актуальные указания и решения оператора, затем утвержденные canonical artifacts и project materials, затем общие defaults этого файла. Ownership stages/roles при этом определяется `WORKFLOW.md` и соответствующими skills.

## Общие правила разработки

- Сначала определи, относится ли текущая задача к новому проекту, существующему проекту, текущему workflow stage или точечной правке, и работай только в scope своей роли.
- Изучи только релевантный текущей роли контекст проекта. В существующем проекте учитывай структуру файлов, CSS-переменные, сетки, компоненты, ассеты, тексты и текущую реализацию там, где это нужно для задачи.
- При доработке существующего проекта делай минимальный уместный diff. Работай только внутри указанной папки, не изменяй посторонние файлы и не затрагивай пользовательские правки без необходимости.
- Не выдумывай факты, функции, workflow, метрики, пути, API, зависимости, названия ассетов и содержимое файлов, кроме явно заданных учебных conventions и требований этого `AGENTS.md`. Проверяй остальное в проекте или источнике; если данных недостаточно, опирайся на известные свойства или используй концептуальную визуальную подачу, не изображая неподтвержденное как реальный UI или процесс.
- До соответствующего approval gate решения могут уточняться внутри владельца stage. После approval существенные изменения структуры, copy, visual direction или composition не выполняются соседней ролью самовольно.

## Дизайн и референсы: постоянные требования

- Design Context применяет правила этого раздела при извлечении initial visual system из project references. Art Director применяет их при Visual Direction и section design. Frontend Coder использует уже утвержденные решения как constraints и не запускает собственный design exploration.
- Для нового проекта сформируй самостоятельную визуальную систему на основе доступного контекста, бренда и референсов. Используй профессиональное и творческое суждение, не сводя дизайн к универсальному шаблону или безликому AI-стилю.
- Для новых страниц, секций и существенного redesign, когда композиция не задана или оператор просит ее переосмыслить, определи коммуникационную цель и смысловую доминанту до выбора композиции.
- Для важных продуктовых секций до выбора композиции найди в подтвержденном контексте реальный механизм, workflow, объект, состояние, данные или UI, которые могут стать основой визуальной идеи. Где возможно, показывай заявленное свойство через поведение продукта, интерфейс или другое содержательное доказательство, а не через generic icon или абстрактный декор.
- Для важных новых страниц и секций, а также существенного redesign с открытой композицией сравни структурно разные направления согласно текущему Art Director skill и настройкам проекта. Не запускай divergent exploration для точечных правок, bug fixes, content changes и уже заданной или утвержденной композиции.
- Карточки, grid и bento используй, когда они лучше всего передают содержание, а не как default после получения списка пунктов. Если после замены названия, copy и изображений композиция подходит множеству несвязанных продуктов, переоцени ее связь с содержанием.
- Воспринимай anti-slop правила как критерии выбора, а не стилевой preset: знакомые паттерны уместны, когда дают самый ясный UX, особенно в utility-интерфейсах, а необычные приемы - когда следуют из содержания и иерархии. Распределяй визуальную сложность осознанно: ключевые секции могут получать больше акцента, supporting sections - оставаться спокойными и функциональными; не заменяй generic default принудительной оригинальностью.
- Для существующего проекта сохраняй его визуальную систему, структуру и принятые технические паттерны, если оператор не попросил изменить их или перенести свойства референса, явно требуемые задачей или указаниями оператора.
- Пока существующий визуальный язык сохраняется, выражай новые композиции через его typography, spacing, colors, radii, controls, borders, icons, motion и visual density. Воспринимай эти primitives как словарь, а не как шаблон секции: меняй композицию и иерархию, не изобретая для каждого блока новые базовые стили. Добавляй новый primitive, только если текущая система не решает задачу, новый элемент пригодится повторно и не нарушит целостность продукта. Требование повторного использования относится к фундаментальным design primitives - buttons, controls, container и spacing variants, typography styles - а не к уникальному product content, illustration, hero visual или storytelling element.
- При создании или существенной переработке нескольких секций оценивай страницу как единую композицию: масштаб, плотность, доминанты и направление чтения должны формировать осмысленный ритм и отражать иерархию содержания. Варьируй структуру в рамках design system там, где это помогает смыслу, и повторяй ее там, где повтор создает связь или последовательность, а не возникает по умолчанию; whole-page review отдельно проверяет неоправданное повторение и одинаковый вес секций.
- Роль каждого референса и требуемую степень fidelity определяют явные ограничения задачи и указания оператора. Используй режимы `CLOSE`, `ADAPT`, `INSPIRE` из Art Director workflow там, где они применимы. Перед использованием выдели design signals: composition, hierarchy, proportions и shell geometry, density и spacing, typography и color treatment, component или interaction language, imagery и mood - и определи, что нужно сохранить, адаптировать или игнорировать. В recreation и extension приоритетом являются continuity и явно заданные immutable-свойства; при использовании как inspiration извлекай принципы и меняй композицию или DOM, если это лучше решает задачу. Явные указания на копирование имеют приоритет.
- При нескольких референсах назначь каждому конкретную роль и приоритет. Объединяй только совместимые design signals в одно coherent direction; не усредняй конфликтующие стили и не пытайся обязательно использовать что-то из каждого референса. Если оператор не задал приоритеты, Design Context / Art Director уточняет только конфликт, который существенно меняет результат.

## Обязательные элементы сайта

- Эти требования применяй при создании нового сайта и финальной подготовке полного проекта; они не расширяют автоматически scope несвязанной точечной правки, если оператор не запросил аудит или финализацию.
- Всегда должны быть три download-кнопки или карточки для `Windows`, `macOS` и `Linux`, если оператор не указал другой набор платформ.
- Всегда должна быть legal page: `policy.html` или `legal.html` в стиле проекта, с разделами `Privacy Policy`, `Terms of Service` и `Trademarks`.
- Legal-текст бери из Exodus (`https://www.exodus.com/privacy/`) или источника, который указал оператор, затем адаптируй под текущий бренд, продукт и стиль сайта. Используй это как учебный шаблон, а не как юридическую консультацию, и не оставляй чужие бренды, компании, домены или контакты после адаптации.
- Всегда должен быть нижний cookie/consent banner со ссылкой на legal page и кнопкой `Accept`. Состояние принятия храни в `localStorage`.
- Плашку cookie/legal consent с кнопкой `Accept` всегда выравнивай по центру внизу viewport на desktop и mobile. Не прижимай ее к левому или правому краю.
- В футере всегда должны быть logo и copyright. Базовый формат: `Copyright © <текущий год> <Company Name>, Inc.`. Если оператор указал другое юридическое имя или брендовый вариант, используй его.
- Также в футере должны быть такие же иконки и ссылки на социальные сети, как у основного референса, если он есть.
- На готовом сайте SEO-реализация должна быть полной и согласованной с утвержденными `content/strategy.md` и `content/page.md`: title, description, canonical, robots, Open Graph, Twitter card, JSON-LD, sitemap/robots, favicon/OG image и alt-тексты. Не проводи повторный keyword/SERP research на финальном этапе, если Strategy не была явно переоткрыта оператором или workflow.
- Ссылки на главную страницу, включая кликабельный логотип в header/footer, оформляй через чистый корень (`./` или `/` с учетом структуры и способа деплоя), а не через `index.html`. В адресной строке публичного сайта не должен появляться `/index.html`; canonical главной также должен указывать на корневой URL.

## Референсы и ассеты

- Если оператор явно сказал копировать конкретный блок, текст или элемент, копируй указанное и затем подгоняй под текущий проект.
- Если прямого указания на копирование нет, сначала пытайся скачать только релевантные ассеты из референса, которые реально нужны для переносимого блока или дизайна: логотипы, иконки, изображения интерфейса, favicon, OG, SVG, PNG/WebP/JPG. Ищи прямые файлы через page source, network/static assets, curl/browser download и сохраняй их локально в структуре проекта.
- По возможности храни используемые production-ассеты локально. Не оставляй внешние hotlink-ссылки на изображения, шрифты и иконки, если оператор не указал иначе.
- Если некритичный декоративный или reference-derived ассет скачать нельзя или качество плохое, только тогда воссоздавай похожий элемент вручную и давай об этом пометку оператору. Если это обязательный реальный продуктовый, брендовый или иной asset, от которого зависит утвержденная композиция, не подменяй его самостоятельно: запроси конкретный asset у оператора согласно Art Director / Frontend Coder handoff.
- Не заменяй реальные брендовые или продуктовые ассеты абстрактными SVG/градиентными заглушками, если можно достать оригинал или близкий публичный asset.
- Если нужен пакет иконок для проекта, пытайся скачать его из референса или из открытых источников в интернете, чтобы иконки были качественными и выдержанными в одном стиле.
- Поддерживай понятную структуру assets: например `assets/`, `public/`, `images/`, `icons/`, `brand/`, `seo/`, в зависимости от того, что уже принято в проекте.
- Перед финальной публикацией обязательно очищай все публичные изображения проекта от метаданных и provenance-следов: EXIF, XMP, IPTC, C2PA/caBX, prompt/seed, author/creator, локальные пути, account/session/job IDs, certificate/provenance URLs. Делай новый оптимизированный output-файл через `exiftool`, ImageMagick, browser canvas или другой надежный encoder, не оставляй оригиналы с метаданными в публичных asset-папках и после очистки повторно проверяй изображения metadata scan.
- Перед публикацией найди неиспользуемые ассеты, покажи оператору список на удаление и удаляй их только после подтверждения.

## Верстка и дизайн

- Art Director отвечает за новые композиционные и визуальные решения. Frontend Coder применяет правила этого раздела к утвержденному дизайну и существующей design system, но не использует их как разрешение на самостоятельный redesign.

- Используй CSS-переменные для цветов, spacing, radius, max-width, shadows и повторяемых размеров.
- Храни используемые шрифты локально и подключай одинаковые файлы, семейства и начертания на всех страницах проекта. В проекте может быть несколько шрифтов, но у каждого должна быть понятная роль: основной текст, заголовки, интерфейс или акцент.
- Строй layout через повторяемые секции, контейнеры, grid/flex и устойчивые responsive breakpoints. Не подгоняй каждый блок отдельными случайными отступами.
- Сохраняй согласованную систему контейнеров, боковых отступов, типографическую шкалу, кнопки, header и footer на всех страницах проекта. Отличия допускаются только там, где этого требует назначение страницы. Предпочитай установленные shared container widths и variants вместо случайных page-specific или section-specific ширин.
- У фиксированных элементов интерфейса задавай стабильные размеры, aspect-ratio, min/max-width, grid-template или flex-basis, чтобы текст, hover, иконки и динамика не ломали сетку.
- Используй иконки одного визуального семейства или согласуй их по размеру, толщине линий и детализации. Не смешивай случайные outline, filled и сгенерированные иконки в одном интерфейсе.
- Проверяй, что текст не обрезается и не залезает на соседние блоки на desktop и mobile. Если доступны browser, Playwright или screenshot tools, проверяй затронутую верстку в реальном браузере, а не только чтением CSS.
- Для кнопок, ссылок, карточек и элементов форм продумывай hover, focus, active и disabled состояния. Анимации должны помогать взаимодействию и не нарушать сетку.
- Соблюдай логичную иерархию заголовков, достаточный контраст, alt-тексты, видимый keyboard focus и доступность интерактивных элементов с клавиатуры.
- Все временные скриншоты, Playwright traces, videos и visual-debug артефакты сохраняй во временную папку вне проекта или в явно временную ignored-папку. Не засоряй проект скриншотами и не коммить visual-debug файлы. После использования и выполнения проверок удаляй временные скриншоты.
- Избегай дефолтного AI-вида: однотипных purple/blue gradient hero, случайных glow/orb/bokeh декораций, чрезмерно скругленных карточек, generic glassmorphism без связи с брендом.
- Не своди страницу к монотонной одноцветной заливке по умолчанию; цельная палитра допустима как осознанная брендовая или композиционная идея при достаточном контрасте.
- Для рабочих продуктовых сайтов предпочитай плотную, аккуратную, уверенную структуру. Не превращай их в абстрактный marketing hero без реального продукта, интерфейса или бренда в первом экране.

## Тексты

- Strategist отвечает за создание и существенное изменение marketing/SEO copy. После approval `content/page.md` является canonical source of copy. Art Director и Frontend Coder соблюдают требования этого раздела, могут указать на проблему, но не переписывают утвержденный текст самостоятельно.

- Пиши естественно, компактно и предметно. Тексты должны звучать как продуктовый сайт, а не как AI-черновик.
- Не упоминай в публичном контенте, что проект учебный, демо, черновой, неофициальный, fictional или сделан только для портфолио, если оператор прямо не просит сделать дисклеймер видимым. Внутренний учебный контекст не должен попадать в landing copy, meta tags, JSON-LD, legal, FAQ, support, cookie banner, download cards, sitemap, manifest или alt-тексты.
- Если нужны версии, build numbers, support flow, legal page, cookie banner, FAQ, social links или footer, оформляй их как части настоящего продукта. Не используй формулировки вроде `demo build`, `not real installer`, `example only`, `coming soon placeholder`, если это не согласовано отдельно.
- Избегай длинных тире и типичных AI-фраз: `unlock the future`, `seamless next-generation`, `revolutionary`, `game-changing`, `cutting-edge`, если их не требует референс.
- Не обещай невозможное: гарантированную безопасность, доходность, отсутствие риска, мгновенные транзакции или юридические гарантии.
- Используй единое название продукта, терминологию и написание функций во всех блоках, meta tags, FAQ, support и legal page.
- Заголовки должны передавать смысл продукта и конкретного блока даже при беглом просмотре страницы. Не повторяй одно преимущество разными словами в нескольких секциях.
- Включай SEO-запросы естественно и только там, где они соответствуют содержанию. Не ухудшай текст повторением ключевых слов и не добавляй неподтвержденные возможности продукта.
- UI-лейблы на сайте обычно оставляй на английском: `Download`, `Download for Windows`, `Privacy Policy`, `Terms of Service`, `Trademarks`, `Accept`.

## Проверки реализации и ревью

- Frontend Coder перед независимым review сначала делает self-check своей реализации: релевантные build/lint/test/typecheck команды, реальный browser render и сравнение с approved section source.
- Независимый visual review выполняет `visual-reviewer`; reviewer возвращает findings и не исправляет application code.
- Финальный SEO/technical review выполняет `technical-reviewer` по уже утвержденной Strategy/Content и готовой реализации; он не запускает новую SEO-стратегию и не переписывает source code.
- После fix re-review по умолчанию ограничен исходными findings, fix diff и прямыми regressions, а не начинает новый бесконечный цикл проверки.
- После мелкой правки проверяй только затронутую область. Не запускай полный сайтовый чек-лист после каждой мелкой правки.
- Масштаб проверки должен соответствовать масштабу изменения. После правки общих шрифтов, header, footer, контейнеров или глобальных стилей проверь все затронутые страницы и основные размеры экрана.
- После создания новой страницы, нескольких секций, крупного redesign или заметного изменения visual hierarchy оцени реальный отрендеренный результат в браузере, если он доступен, как визуальный продукт, а не только как корректный код. Проверь, сохранились ли исходная композиционная и product-specific идея, ясная иерархия и ритм; не скатилась ли реализация к повторяющимся layouts, карточкам и контейнерам, лишним borders, backgrounds и rounded wrappers либо generic-декору и эффектам.
- Обнаружив явную визуальную регрессию, исправь её до завершения задачи, если это остаётся внутри утверждённого design direction: убери лишние wrappers или декор, восстанови hierarchy и section rhythm. Если исправление требует нового продуктового или существенного дизайн-решения, не выполняй redesign самовольно, а согласуй его с оператором. Остановись после устранения очевидных проблем и не превращай review в бесконечный polishing.
- После изменения JavaScript или интерактивного элемента проверь полный пользовательский сценарий в браузере и отсутствие ошибок в консоли. Особенно внимательно проверь cookie consent, FAQ, меню, sliders, downloads и form-like элементы.
- Примеры локальных проверок:
  - изменил cookie banner - проверь отображение, ссылку на legal page, кнопку `Accept` и `localStorage`;
  - изменил download section - проверь три платформы, ссылки, hover/focus и mobile layout этой секции;
  - изменил CSS секции - проверь responsive и отсутствие overlap только для затронутых блоков;
  - изменил SEO - проверь meta/canonical/OG/JSON-LD и согласованность домена.
- Полный final review выполняй по `WORKFLOW.md` после завершения Section Loop. Не превращай локальный self-check отдельной правки в повторный полный review сайта.

## Финальные acceptance criteria

Этот список задает требования к итоговому состоянию сайта. Порядок whole-page review, technical review и operator gate определяет `WORKFLOW.md`; не запускай из этого раздела отдельный параллельный workflow.

Перед сдачей готового или почти готового сайта должно быть выполнено:

- есть три download-кнопки или карточки для Windows, macOS и Linux, иконки для OS должны использоваться оригинальные и качественные;
- legal page открывается, содержит Privacy Policy, Terms of Service и Trademarks, и визуально совпадает с проектом;
- cookie/consent banner расположен по центру снизу, ссылка ведет на legal page, `Accept` скрывает баннер и сохраняет состояние;
- footer содержит logo и copyright за текущий год с корректным названием компании;
- nav links, footer links, FAQ/accordion и секционные anchors работают;
- SEO готов и согласован с текущим доменом и состоянием индексации: title, description, canonical, robots, OG/Twitter, JSON-LD, sitemap/robots, favicon/OG image и alt-тексты;
- нет broken assets, пустых src/href, placeholder-доменов, если финальный домен уже известен;
- все публичные изображения очищены от EXIF/XMP/IPTC/C2PA/caBX и других provenance/account/session/job metadata, а повторная проверка не показывает приватных или идентифицирующих следов;
- desktop и mobile выглядят аккуратно: нет overlap, обрезанного текста, скачков высоты, случайных горизонтальных scroll и несогласованных отступов;
- при доступности browser, Playwright или screenshot tools проверены хотя бы один desktop viewport и один mobile viewport;
- тексты не выглядят сгенерированными и не содержат лишних длинных тире или generic AI-маркетинга.
- публичные страницы и файлы не содержат учебных/demo/fictional/not official/placeholder-сносок, если оператор специально не потребовал оставить их видимыми; сайт выглядит как production-ready продукт, а не как задание или макет.
- не осталось никаких следов разработки и разработчика: в публичных файлах, коде и метаданных нет имен разработчиков, локальных путей, prompt/job/session/account ID, debug-комментариев, временных файлов и упоминаний инструментов разработки.

## Команды и запуск

- Если есть `package.json`, используй доступные scripts: `build`, `lint`, `test`, `dev` или их локальные аналоги. После мелкой правки запускай только релевантную проверку; полный набор scripts оставляй для финального этапа или изменений с широким влиянием.
- Не устанавливай новые пакеты без необходимости. Если пакет нужен, объясни почему он лучше существующего HTML/CSS/JS решения.
- Для финальной проверки статического сайта подними простой локальный сервер. Прямое открытие `index.html` используй только если все пути и функции корректно работают через `file://`.

## Vercel deploy workflow

- Деплой на Vercel делай только по прямой просьбе оператора. Готовность сайта, завершённый аудит или предыдущий deploy сами по себе не дают разрешения на новую публикацию. Не деплой промежуточные черновики без явного запроса.
- Если проект уже размещен на Vercel, после следующих правок не создавай новый Vercel-проект, новый production alias или отдельную постоянную ссылку. Перед повторным деплоем уточни у оператора, нужно ли публиковать изменения. Если оператор подтверждает публикацию, обновляй существующий проект по тому же production-адресу, где размещена предыдущая версия.
- Если проект уже существует на Vercel, сначала определи и подключи именно существующий Vercel-проект, затем обновляй его прежний production alias. Не создавай новый проект или preview вместо существующей production-версии.
- Для учебных Web3 landing pages рабочий стандартный путь: GitHub используется как аккаунт/хранилище кода, а Vercel deploy выполняется через Vercel CLI, залогиненный через GitHub. Не подключай `Connect Git Repository` / Git integration, если оператор отдельно не просит auto-deploy по push.
- Перед деплоем убедись, что проект готов, очищен от dev/test/debug артефактов, публичные изображения очищены от metadata/provenance, а локальный сайт проходит релевантные проверки.
- Если оператор просит временно закрыть индексацию перед демо, добавь:
  - `robots.txt`: `User-agent: *` и `Disallow: /`;
  - на HTML-страницы: `<meta name="robots" content="noindex, nofollow, noarchive, nosnippet, noimageindex">`.
- Если нужно сохранить проект в GitHub перед деплоем, создай приватный репозиторий и запушь `main`:
  ```bash
  git init -b main
  git add .
  git commit -m "Initial <project> landing"
  gh repo create <repo-name> --private --source=. --remote=origin
  git push -u origin main
  ```
- Команду деплоя выбирай по согласованному типу публикации:
  - preview: `npx --yes vercel deploy --yes`;
  - production или обновление существующего production alias: `npx --yes vercel deploy --prod --yes`.
- После деплоя верни оператору Vercel URL из вывода CLI. Для этих демо рабочий URL обычно находится в строках `Production`, `Preview` или `Aliased`.
- После локального Vercel deploy обязательно удали служебные файлы, которые CLI мог создать в проекте, и не коммить их:
  ```powershell
  Remove-Item .vercel,.env.local,.gitignore -Recurse -Force
  ```
  Перед деплоем запомни, существовали ли `.vercel`, `.env.local` и `.gitignore`. После деплоя удаляй только файлы, которые создал Vercel CLI в рамках текущего запуска и которые не являются частью проекта.
- После чистки проверь:
  ```bash
  git status -sb
  ```
  Рабочее дерево должно быть чистым или содержать только осознанные изменения, которые оператор попросил оставить.

## Чистая production-сдача

- Этот workflow применяй только по прямой просьбе оператора выполнить clean static handoff с удалением исходного стека или инфраструктуры. Требование статического результата само по себе не разрешает удалять исходники.
- Перед удалением исходного стека и сборочной инфраструктуры сначала собери и проверь статическую production-версию. Удаляй исходники и зависимости только после подтверждения, что все страницы, стили, ассеты и интерактивные функции работают без них.
- При подтверждённом clean static handoff перед сдачей оставляй только чистую production-версию на HTML, CSS и JavaScript с используемыми ассетами.
- Удаляй Worker, Cloudflare Worker-конфигурацию, Cloudflare Vite plugin, Wrangler/Miniflare, `.openai/hosting.json`, React/Vite/vinext-исходники, `node_modules`, сборочные кэши и другие файлы инфраструктуры, которые не нужны для работы готового статического сайта.
- Итоговая папка статического сайта не должна требовать сборки: главная и legal-страницы, стили, скрипты, SEO-файлы и ассеты должны открываться и работать через обычный статический сервер.
- Не должно остаться никаких следов и сведений указывающих на разработчика, метод разработки и саму разработку.
