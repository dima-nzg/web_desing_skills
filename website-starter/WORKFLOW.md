# Website AI Workflow

Версия: v1
Назначение: разработка качественных маркетинговых сайтов и лендингов с AI-агентами.

## Start here

Перед новым сайтом оператор:

```text
1. Создает новую папку проекта
2. Копирует туда website starter
3. При необходимости корректирует AGENTS.md под конкретный проект
4. Открывает проект в Codex
5. Проходит WORKFLOW.md сверху вниз
```

На старте в проекте уже есть только фундамент:

```text
AGENTS.md
WORKFLOW.md
.agents/skills/
.codex/agents/
.codex/config.toml
references/
content/
design/
```

Основные проектные файлы появляются уже в процессе:

```text
Старт проекта
→ PRODUCT.md

Strategy / SEO / Funnel
→ content/strategy.md

Design Context
→ DESIGN.md

Content Wireframe
→ content/page.md

Visual Direction / Section Design
→ design/approved-direction/
→ design/approved-sections/
```

`PRODUCT.md` и `DESIGN.md` заранее пустыми не создаются. Их формируют соответствующие этапы workflow на основании реальных данных проекта.

---

## 1. Как устроена система

### Инструкции

- `AGENTS.md` - общие правила для агентов, а также правила для типичных типов проектов. Здесь фиксируются стек, структура репозитория, ограничения, ключевые файлы и другие постоянные рабочие условия.
- `WORKFLOW.md` - инструкция для оператора: в каком порядке вести новый проект, какие этапы проходить и какие результаты получать.
- `.agents/skills/` и `.codex/agents/` - инструкции для специализированных ролей и повторяемых задач.

### Контекст конкретного проекта

- `PRODUCT.md` - продукт, аудитория, позиционирование, цель, особенности, ограничения и подтвержденные факты.
- `DESIGN.md` - визуальная система проекта: типографика, цвета, компоненты и основные дизайн-правила.

Проектные результаты сохраняются в отдельных файлах, чтобы следующий этап получал готовый контекст и утвержденные решения.

## Опционально: инструменты дизайна

### Impeccable

Если оператор хочет использовать Impeccable в проекте, установить его в начале проекта из корня репозитория:

```bash
npx impeccable install
```

После установки перезапустить / reload используемый AI coding tool.

Impeccable не является обязательной частью workflow. Он используется как набор инструментов для design context, генерации/итерации, critique, hooks и финальной доводки.

`PRODUCT.md` и `DESIGN.md` остаются canonical-файлами нашего workflow.

### Mobbin MCP

Если у оператора есть доступ к Mobbin MCP, подключить или проверить его доступность **до начала работы над дизайном**.

Mobbin MCP доступен на платных планах Mobbin, поддерживает OAuth и не требует ручной настройки API key.

Для Codex App Mobbin сначала подключается в ChatGPT, после чего Codex App использует те же credentials.

Mobbin используется Art Director как инструмент targeted reference research: поиск реальных UI/web patterns по конкретной задаче блока.

Если Mobbin MCP недоступен, workflow не блокируется — Art Director использует Web Search и специализированные reference-площадки.

Mobbin и Impeccable решают разные задачи:

```text
Mobbin / Web references -> искать удачные реальные решения и композиционные идеи
Impeccable             -> создавать, изменять, проверять и полировать наш UI
```

Impeccable examples/components не используются как случайная библиотека референсов только потому, что они доступны внутри набора инструментов.

### DataForSEO

Если для проекта планируется режим `SEO VERIFIED`, до запуска Strategist оператор проверяет, что credentials и SEO tool / CLI wrapper для DataForSEO работают.

Если DataForSEO не подключен, используется режим `FREE`; workflow не блокируется.

## 2. Общий workflow

### Этап 0. Инициализация проекта

Собрать исходные данные:

- что за продукт;
- кто пользователь;
- главное целевое действие;
- тип проекта;
- особенности проекта;
- существующий сайт или продукт;
- основные визуальные референсы, если есть;
- бренд-материалы, если есть;
- уже доступные product screenshots, видео, фото, анимации и другие реальные ассеты, если они есть;
- ключевые ограничения;
- технический стек.

На старте достаточно нескольких основных референсов, которые задают общий visual language. Искать заранее отдельный референс для каждого будущего блока не требуется — недостающие block-level references Art Director найдет позже через targeted research.

Полный набор ассетов заранее собирать тоже не требуется. На старте фиксируется только то, что уже есть; точные требования к недостающим ассетам определяются позже на уровне конкретных блоков.

Создать или обновить:

- `PRODUCT.md`
- `AGENTS.md`
- папку `references/`

Результат этапа: агент понимает, что мы строим и в каких рамках.

---

### Этап 1A. Strategy / SEO / Funnel

Роль: `strategist`

Цель этапа: быстро получить надежную смысловую, SEO- и конверсионную основу страницы до начала дизайна.

#### Перед стартом

Оператор выбирает режим:

```text
Используем DataForSEO?
├─ Нет -> FREE
└─ Да  -> SEO VERIFIED
```

- `FREE` — Web Search, browser, анализ конкурентов и SERP, работа GPT с найденными данными.
- `SEO VERIFIED` — то же самое + DataForSEO для расширения и количественной проверки ключей и SERP.

#### Что дает оператор

Данные из `PRODUCT.md`:

- продукт и аудитория;
- главное целевое действие;
- язык и география;
- особенности проекта;
- известные конкуренты / референсы;
- важность SEO для проекта.

#### Что делает Strategist

За один автономный проход:

1. изучает продукт, референсы и конкурентов;
2. исследует поисковый спрос и search intent;
3. собирает и группирует релевантные keyword/topic clusters;
4. проверяет основные направления по SERP;
5. строит funnel;
6. предлагает структуру страницы;
7. готовит смысловой brief для каждого блока.

В режиме `SEO VERIFIED` ключевые SEO-решения дополнительно проверяются через DataForSEO.

#### Результат

Один файл:

`content/strategy.md`

В нем:

- продукт / аудитория / целевое действие;
- основные выводы по конкурентам;
- SEO intent и основные keyword/topic clusters;
- funnel;
- рекомендуемая структура страницы;
- brief по каждому смысловому блоку;
- идеи отдельных SEO-страниц, если они нужны;
- режим исследования и важные неподтвержденные допущения.

#### Взаимодействие с оператором

Обычный сценарий:

```text
Оператор -> дает исходные данные и выбирает режим
Strategist -> исследует и создает strategy.md
Оператор -> один review / корректировка
```

После завершения 1A отдельно переходить к Stage 2 еще рано: сначала должен завершиться параллельный Stage 1B.

---

### Этап 1B. Design Context

Роль: `design-context`

Цель этапа: быстро превратить референсы и существующие визуальные материалы в начальную дизайн-систему проекта, которой дальше смогут пользоваться Art Director, Reviewer и Coder.

Этот этап можно запускать параллельно с Strategy.

#### Что дает оператор

- основной референс или несколько референсов;
- screenshots / бренд-материалы, если есть;
- существующий UI продукта, если есть;
- короткие указания, что нужно сохранить или можно копировать близко, а что является только источником вдохновения.

Оператор не должен вручную выписывать цвета, шрифты, spacing и другие параметры, если агент может определить их сам.

#### Что делает Design Context Agent

За один проход:

1. изучает визуальные референсы и доступные материалы;
2. выделяет устойчивые визуальные принципы проекта;
3. фиксирует палитру, типографику, геометрию, плотность, borders/radii/elevation, component language, работу с иконками, изображениями и product visuals;
4. создает или обновляет корневой `DESIGN.md`;
5. неуверенные решения помечает как provisional, а не выдумывает их как утвержденные правила;
6. отдельно сообщает оператору, что именно не удалось надежно определить, каких материалов или данных не хватает и почему это влияет на дизайн-контекст.

`DESIGN.md` должен оставаться совместимым с форматом Impeccable и использоваться как основной источник визуального контекста проекта.

#### Использование Impeccable

Если Impeccable установлен:

- на новом проекте без сформированной UI-системы можно использовать `/impeccable document --seed` как основу для `DESIGN.md`;
- если уже существует связный UI, tokens или компоненты, используется `/impeccable document` для синхронизации `DESIGN.md` с реальной реализацией;
- `/impeccable extract` на этом этапе не нужен — reusable patterns извлекаются позже, когда они действительно появились в нескольких местах;
- `/impeccable doctor` запускается по необходимости: после установки/обновления, проблем с context/hook или подозрения, что `DESIGN.md` устарел.

Основным оркестратором этапа остается наш skill `design-context`; Impeccable используется как дополнительный инструментарий и совместимый формат.

#### Результат

Основной файл:

`DESIGN.md`

Если используется Impeccable, также может появиться его служебный `.impeccable/design.json`.

#### Взаимодействие с оператором

Обычный сценарий:

```text
Оператор -> дает референсы и важные указания
Design Context -> исследует и создает DESIGN.md
               -> отдельно сообщает о пробелах / provisional-решениях
Оператор -> быстрый review ключевого направления и спорных мест
```

После завершения 1A и 1B оператор **одним проходом** проверяет `content/strategy.md` + `DESIGN.md`, корректирует спорные места и только после этого запускает Stage 2.

---

### Этап 2. Content Wireframe

Роль: `strategist`

Цель этапа: превратить утвержденную стратегию в практически готовый контент страницы: маркетинговый, SEO-оптимизированный и выстроенный по funnel. После этого к смысловой части сайта желательно не возвращаться до финальной мелкой полировки.

#### Перед стартом

Strategist спрашивает оператора, есть ли дополнительные референсы по контенту и подаче.

Оператор может дать:

- сайты, стилю текста которых стоит следовать;
- страницы конкурентов с удачной структурой или подачей;
- конкретные блоки, идеи или приемы, которые стоит адаптировать;
- указания по tone of voice.

Если дополнительных референсов нет, используются `PRODUCT.md`, `content/strategy.md`, основные проектные референсы и результаты предыдущего research.

#### Как проходит этап

Работа идет последовательно, блок за блоком.

Для каждого блока Strategist предлагает **2-3 варианта** содержания.

Каждый вариант должен включать:

- идею блока;
- примерный heading / subheading;
- основной текст;
- CTA, если нужен;
- proof / supporting content, если нужен;
- предполагаемый visual/content asset;
- короткое объяснение простым языком:
  - чем вариант отличается;
  - какую задачу funnel решает;
  - на какой search intent / SEO-темы опирается;
  - почему такой вариант может лучше работать.

Оператор выбирает вариант, комбинирует элементы нескольких вариантов или дает короткую корректировку.

После выбора Strategist фиксирует итог блока и переходит к следующему.

Research по ключам, конкурентам и SERP не запускается заново для каждого блока без необходимости. Основой остается `content/strategy.md`.

#### Требования к тексту

Контент должен одновременно:

- понятно объяснять продукт;
- уверенно вести пользователя к главному целевому действию;
- быть маркетингово убедительным без пустых claims;
- естественно покрывать релевантные SEO-темы и search intent;
- соответствовать выбранному tone of voice и референсам;
- иметь реалистичный объем, с которым уже можно проектировать финальный дизайн.

Основные headings, тезисы, CTA и структура после этого этапа считаются практически финальными.

На поздних этапах допускается только небольшая полировка формулировок, если этого требует дизайн, readability или финальная SEO-проверка.

#### Результат

Основной файл:

`content/page.md`

В нем для каждого утвержденного блока фиксируются:

- назначение;
- финальная идея;
- heading / subheading;
- основной copy;
- CTA;
- proof / supporting content;
- visual/content requirements;
- важные SEO-темы, если они относятся к блоку.

После завершения всех блоков `content/page.md` становится основным источником контента для Art Director и Coder.

### Gate 1

Оператор подтверждает:

- порядок блоков;
- смысл каждого блока;
- основные тексты;
- CTA;
- общий flow страницы.

После этого можно переходить к Visual Direction.

---

### Этап 3. Visual Direction

Роль: `art-director`

Цель этапа: определить единый визуальный язык страницы на реальном контенте до детальной проработки всех секций.

#### Что получает Art Director

- `PRODUCT.md`;
- `DESIGN.md`;
- `content/page.md`;
- основные проектные референсы;
- доступные reference-research tools.

#### Работа с референсами

Оператор не обязан заранее находить референс под каждый блок.

Перед началом работы над конкретным блоком Art Director уточняет у оператора:

```text
Есть ли конкретный reference для этого блока?

Если есть, насколько близко ему следуем?
- CLOSE   — можно близко использовать композицию и приемы;
- ADAPT   — сохраняем сильную идею, но адаптируем под наш контент и систему;
- INSPIRE — используем только как направление / источник идеи.
```

Если подходящего block-level reference нет, Art Director **не переходит сразу к дизайну из головы**. Сначала он делает короткий targeted reference research.

Для research используются:

1. Mobbin MCP, если подключен;
2. Web Search;
3. специализированные reference-площадки для сайтов и секций.

Art Director самостоятельно просматривает достаточное количество кандидатов и отбирает только релевантные идеи. Оператору не нужно отдельно согласовывать весь найденный массив.

Impeccable не используется как primary reference library и не является источником случайных готовых «кубиков» дизайна.

#### Выбор visual direction

Для начала Art Director берет 2-3 наиболее характерных блока из `content/page.md`, например Hero + Product Showcase + еще один важный смысловой блок.

На их основе он создает **2-3 действительно разных отрендеренных visual directions**.

Варианты должны различаться:

- композицией;
- visual hierarchy;
- способом подачи продукта и контента;
- характером секций и visual rhythm;

а не только цветом, radius или мелкими декоративными деталями.

Для каждого варианта Art Director коротко объясняет:

- основную идею;
- какие reference-решения повлияли на вариант;
- почему решение подходит продукту и контенту;
- как оно поддерживает funnel;
- как этот язык можно продолжить на остальных секциях.

#### Как показываются варианты

Предпочтительный формат — реальный browser-rendered mockup / lightweight implementation, а не только словесное описание.

Exploration-код может быть временным и не обязан сразу соответствовать production-качеству.

Если Impeccable установлен, Art Director может использовать его команды и Live Mode для создания и итерации вариантов, но использование конкретной команды не является обязательным.

#### Выбор оператора

Оператор:

- выбирает один direction;
- или комбинирует сильные части нескольких вариантов;
- дает короткие корректировки.

Art Director собирает из этого один approved visual direction.

#### Результат

После утверждения:

- обновляется `DESIGN.md` новыми подтвержденными композиционными принципами;
- сохраняется визуальный reference утвержденного направления, например:

```text
design/approved-direction/
  preview.png
```

Approved direction становится визуальным source of truth для дальнейшей работы над блоками.

Те representative sections из Stage 3, которые оператор уже явно утвердил как готовые по композиции, считаются `approved sections` и в следующем этапе повторно не проектируются. Они переходят сразу к asset check и implementation.

### Gate 2

Общий visual direction утвержден.

После этого начинается повторяемый Section Loop.

---

### Этап 4. Section Loop

Роли:

- `art-director`
- `frontend-coder`
- независимый subagent `reviewer`

Цель: пройти каждый блок от mockup до реального утвержденного section и только после этого переходить к следующему.

Блоки, уже утвержденные в Stage 3, начинают цикл сразу с `Asset & Responsive Check`.

#### 1. Reference check

Перед новым блоком Art Director спрашивает оператора:

```text
Есть ли конкретный reference для этого блока?

Если есть:
- CLOSE
- ADAPT
- INSPIRE
```

Если подходящего reference нет, Art Director делает targeted reference research через Mobbin MCP, Web Search и специализированные reference-площадки.

#### 2. Section mockups

Art Director использует **реальный утвержденный контент** из `content/page.md` и создает 2-3 rendered variants в рамках approved visual direction.

Варианты должны отличаться композицией, visual hierarchy и способом подачи контента, а не только косметикой.

Для каждого варианта коротко объясняется:

- идея;
- reference influence;
- почему решение подходит контенту и funnel;
- какие реальные assets потребуются.

Оператор выбирает вариант, комбинирует несколько или дает точечную корректировку.

После выбора блок считается approved по композиции.

#### 3. Asset & Responsive Check

До начала production implementation Art Director фиксирует, что нужно блоку:

```text
Assets:
- ready
- existing source
- operator input required
- create after design approval

Responsive:
- obvious from system
- custom behavior required
```

Логика по ассетам:

- если нужный screenshot, видео, анимация, фото или другой реальный media asset уже есть — используется его source;
- если такой asset нужен по утвержденному дизайну, но отсутствует — агент **обязательно сообщает оператору и запрашивает его**;
- если точный asset невозможно определить до выбора дизайна, сначала утверждается mockup, затем Art Director формулирует точное требование к asset и запрашивает его перед реализацией;
- отсутствующий реальный asset нельзя молча заменять generic AI-image, случайной иконкой или упрощенной заглушкой.

Для сложных или нестандартных блоков Art Director дополнительно дает mobile mockup либо короткое описание responsive behavior. Для очевидных производных блоков отдельный mobile mockup не нужен.

#### 4. Implementation

Coder получает:

- approved mockup;
- реальные тексты из `content/page.md`;
- готовые assets;
- responsive intent;
- `DESIGN.md`;
- существующие компоненты и технические ограничения.

Coder:

- реализует блок;
- добавляет responsive states и interactions;
- запускает страницу;
- сравнивает render с approved mockup;
- исправляет очевидные visual / functional проблемы до review.

Если Impeccable hooks подключены, они могут работать как фоновая проверка.

#### 5. Independent Review

Отдельный subagent `reviewer` проверяет **реально отрендеренный блок**.

Reviewer смотрит только полезные вещи:

- соответствие approved mockup;
- typography, spacing, proportions, alignment;
- visual hierarchy;
- responsive;
- overflow / layout / interaction bugs;
- случайное упрощение или AI-slop, появившиеся при реализации;
- согласованность с соседними approved sections.

Reviewer возвращает конкретные findings и сам не меняет application code.

Если Impeccable установлен, Reviewer может использовать:

- `critique` для сложных или визуально спорных блоков;
- `audit` / detector для технических проблем.

#### 6. Refinement

Coder / Art Director исправляют только существенные findings.

Специализированные Impeccable-команды (`layout`, `typeset`, `colorize`, `distill`, `bolder`, `quieter` и др.) используются только под конкретно найденную проблему.

`/impeccable polish` запускается только когда композиция, контент и реализация блока уже закончены. Черновые mockups не полируются.

Обычно достаточно одного review/fix прохода. Второй круг в первую очередь проверяет уже исправленные замечания.

Если проблема находится в самом approved mockup, Reviewer сообщает об этом оператору и Art Director вместо скрытого redesign.

#### 7. Operator Approve

Оператор сам смотрит готовый блок в браузере:

- принимает его;
- либо дает последние точечные правки.

Только после operator approve section считается завершенным и начинается следующий блок.

Цикл:

```text
reference / research
      ↓
2-3 mockups
      ↓
operator choice
      ↓
asset + responsive check
      ↓
implementation
      ↓
independent review
      ↓
refinement
      ↓
operator approve
      ↓
next section
```

---

### Этап 5. Final Page Review

Роль: независимый subagent `reviewer`

Режим skill: `whole-page`

Этап запускается после того, как все блоки собраны и каждый отдельно утвержден оператором.

Цель: проверить страницу как единое целое и найти только проблемы, которые не были видны на уровне отдельных секций.

Reviewer смотрит live page целиком:

- общий visual rhythm и переходы между секциями;
- повторяющиеся композиции и слишком похожие блоки;
- баланс плотности и свободного пространства;
- распределение визуальных акцентов;
- цельность funnel от Hero до финального CTA;
- согласованность typography, backgrounds, product visuals и section spacing;
- целостность desktop и mobile версии.

Не нужно повторно разбирать уже approved блоки по мелким деталям, если проблема не проявляется на уровне всей страницы.

#### Инструменты

Reviewer использует:

- skill `reviewer` в режиме `whole-page`;
- browser / screenshots;
- `DESIGN.md`, `content/page.md` и approved sections;
- Impeccable `critique`, `audit` и detector, если они полезны.

Reviewer формирует только конкретные существенные findings и не редактирует application code.

Coder / Art Director исправляют найденные проблемы. Если требуется финальная полировка, `/impeccable polish` используется только после того, как структура всей страницы уже окончательно утверждена.

Обычно достаточно одного review/fix прохода.

---

### Этап 6. Final SEO / Technical Pass

Роль: тот же независимый subagent `reviewer`

Режим skill: `seo-tech`

Цель: убедиться, что готовая страница технически корректна, соответствует утвержденной SEO-стратегии и не теряет конверсии из-за ошибок реализации.

Reviewer сверяет live page и код с:

- `PRODUCT.md`;
- `content/strategy.md`;
- `content/page.md`.

Проверяется только финальная реализация:

- `title`, meta description, canonical;
- H1-H6 и semantic HTML;
- internal links;
- Open Graph;
- images / alt;
- robots / sitemap;
- structured data, если она нужна проекту;
- accessibility;
- performance;
- console / layout / interaction errors;
- корректность CTA, download links, forms и основных пользовательских действий.

DataForSEO на этом этапе обычно не нужен: keyword strategy уже утверждена раньше. Повторный внешний SEO research запускается только если обнаружилось существенное расхождение с первоначальной стратегией.

#### Инструменты

Reviewer использует:

- skill `reviewer` в режиме `seo-tech`;
- browser;
- shell / project checks;
- Impeccable `audit` / detector, если установлен;
- доступные технические проверки проекта.

Reviewer возвращает короткий список конкретных проблем.

Coder исправляет findings и запускает необходимые project checks повторно.

### Gate 3

AI review завершен. Сайт готов к финальной проверке оператором.

---

### Этап 7. Final Human Review & Release

Оператор проходит готовый сайт целиком как пользователь.

Проверить:

- общий внешний вид;
- desktop и mobile;
- тексты и CTA;
- основные interactions;
- ссылки / download flow;
- нет ли оставшихся заметных визуальных или функциональных проблем.

На этом этапе допускаются только финальные точечные правки. Если обнаружена фундаментальная проблема, она возвращается в соответствующий этап workflow.

После финального approve сайт считается готовым.

Deploy / release выполняется только по явной команде оператора.

---

### Этап 8. Retrospective

После проекта сделать короткий retrospective без отдельного большого отчета.

Сохранить только то, что реально пригодится в следующих website-проектах:

- повторяющиеся ошибки;
- удачные изменения workflow;
- полезные приемы для skills / `AGENTS.md`;
- сильные визуальные решения для собственной reference library.

Не переносить единичный случай в глобальное правило без причины.

Если несколько реализованных UI-patterns действительно повторяются, на этом этапе можно использовать Impeccable `extract` для их выделения в reusable patterns.

Цель retrospective — сделать следующий проект быстрее и стабильнее, а не документировать всё, что произошло.
